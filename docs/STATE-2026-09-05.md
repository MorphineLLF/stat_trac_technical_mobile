## 🔴 THE OPEN BUG — start here

**Reported by the user at the end of the session: "cert reached server but no
test data."** A certificate uploaded, its 23 measurement lines did not.

### What is known, measured not assumed

| | |
|---|---|
| Local `test_certificates` | 2 rows — ids 1 and 2 |
| Local `test_outputs` | 23 lines each, for both certificates |
| Local signatures | cert 1 tech 1520 bytes, cert 2 tech 1184 bytes. **No client signature on either, `client_name` empty on both** |
| `upload_queue` | **empty** |
| Synced `TestCertificate` with a `TestMobileID` | **0** (the device's own copy may lag the server) |
| Dart errors in the run log | none |

Certificate 2 was created at **22:14:01**, and the build carrying the queue
wiring started at **22:11:41** — so it was created *after* the wiring was live.

### The reasoning that narrows it

`CertificateRepositoryImpl.issueCertificate` is **local only** — it saves the
certificate, the outputs and the equipment and makes no network call. So the
outbox is the only path to the server.

**A batch is all-or-nothing server-side.** If the line ops had been sent and
refused, nothing would have been applied and the certificate would not be on
the server either. A certificate arriving *without* its lines therefore means
**the batch contained no line ops** — `_outputs` was empty when
`_queueForUpload` built it.

That is the hypothesis to test first. It is not proven.

### Why it is not yet proven

The queue row is deleted on success, so the evidence of what was sent is gone.
`_queueForUpload` reads `_outputs`
(`create_certificate_screen.dart:166`), the same field
`issueCertificate` receives at line 107 — and that call demonstrably saved 23
outputs locally. So the two reads should agree, and the fact that they appear
not to is the thing to explain.

`_outputs` is assigned only at line 303, via `onOutputsChanged` from
`CertTestGrid`.

### What to do next, in order

1. **Add diagnostics before changing anything.** Log the line count at
   `_queueForUpload`, and log the queue row before the immediate drain. One
   run then says whether the batch was built empty or built full and lost its
   lines. Do not guess between those two — they have different fixes.
2. If built empty, trace `onOutputsChanged` — whether the grid reports its
   rows before Save runs, and whether a rebuild resets `_outputs`.
3. Only then fix.

**Do not delete the queue row on success until this is understood** — or add a
`sent` archive — because the current design destroys the evidence.

## 🔴 SIGNATURES — the certificate is not valid without them, and they cannot sync

The user's other point, and it is correct: **the printed PDF will differ from
what the technician signed.**

- The technician signature **is** captured — 1,184 and 1,520 bytes on the two
  local certificates.
- `bytea` crosses **neither** the sync stream nor the upload allowlist.
- So a signature exists only on the device. The office renders a PDF from
  server data, which has no signature on it.

**A certificate is not valid without its signatures**, so today a technician
can complete work on-device that can never become a valid certificate. This is
the single biggest open item and it is with the user, not with this app.

Also unresolved on the device: **no client signature and no `client_name` was
captured on either certificate**, though the wizard has a facility-contact
field. Worth checking whether the signature step is reached and completed at
all, separately from the transport question.

## The upload contract

Full detail in `docs/sync-client-handover.md` §§11–14. The essentials:

```
POST /{company}/sync/upload     Bearer device token (a cookie gets 403)
{"ops":[
  {"table":"TestCertificate","mobile_id":"<uuid>","data":{...}},
  {"table":"TestOutput","mobile_id":"<uuid>",
   "data":{"TestOutputCertMobileID":"<cert uuid>", ...}},
  {"table":"TestCertificate","mobile_id":"<uuid>","action":"issue",
   "data":{"verdict":1,"next_service":"...","complete_pm_work_order":true,
           "complete_pm_job_card":false}}
]}
```

- **A line names its certificate by `TestOutputCertMobileID`**, never
  `TestOutputCertID` — the device cannot know the server key. A `0` there is an
  orphan, and the register holds 8,850 of those.
- **`verdict` is required and never defaulted.** `0` is Non-Compliant.
- **Unknown fields on an issue op are REFUSED, not dropped** — the opposite of
  the row-op allowlist. Spell the five exactly.
- **422 ≠ 400.** 400 means the app is broken; 422 means understood and refused,
  and retrying never helps. `not_found` also means out of scope.
- **Trust the 409 `differs` flag; never re-derive it.** The app sends JSON, so
  an int arrives as a double — a text comparison would call `9304` and `9304.0`
  different.

## Dead columns — a whole class of silent bug

**`AssetNextServiceDate` and `AssetLastServiceDate` are NULL on all 5,121
assets.** Not sparse — dead register-wide. A check written against either fires
for nothing while looking like it works.

This produced the expired-analyser bug: every instrument stayed selectable
because none was ever expired. **Calibration due is the instrument's
`AssetPmTask` schedule date**, read as
`max(PmTaskScheduleDate)` per instrument — a scalar subquery, never a join
(a join lists an instrument once per task), and never matched by description
(the register already spells it three ways). That mirrors the desktop, which
has done it since 2026-09-02.

**Two more places still read the dead column and are quietly wrong:**

1. The Assets screen's **"Service Due"** tile — can only ever be 0.
2. The **"SVC DUE"** badge in the asset list, and both service dates on asset
   detail.

An asset's next service almost certainly also lives in `AssetPmTask`, but that
is an inference and inferring the source is exactly the mistake that caused the
calibration bug. **Ask, do not assume.**

## The lesson that cost the most time

**Seven read paths were still pointed at dead sources; six were found by the
user hitting them.** Assets stats → picker dialog → PM tasks → test equipment →
templates → asset detail.

A dead read is invisible until someone opens that screen: the app compiles, the
query runs, and the answer is an honest empty list. Two preventions, both now
applied at least once:

1. **Audit structurally.** Enumerate every provider and trace what it
   *ultimately* reads. A grep for the data source is not enough —
   `templatesByType` reached it through the *repository*.
2. **Make the wrong source unrepresentable.** `showAssetPicker` takes
   `PowerSyncAssetDataSource`, so the compiler rejects the dead one.

**Work orders have not been repointed at all. Do the audit first.**
