## 🔴 THE NEXT THING THAT MUST BE BUILT: the certificate upload endpoint

**This is the blocker for everything on the write side, and it is server-side.**

The Go application has the entire certificate lifecycle already —
`internal/stats/certificate_write.go`, 1,276 lines: `StartTest`,
`SaveTestLine`, `IssueCertificate`, `VoidCertificate`, `SaveSignature`. What
does not exist is a route a handset can post to. `sync_push.go` covers the rep
entities (accounts, visits, issues) and **not** work orders or certificates.

### The contract the app must satisfy — `IssueInput`

Issuing a certificate is **not** saving a row. It is one transaction that also
moves the PM task's schedule date, completes or raises a PM work order, writes
a job card, releases the task and writes audit lines. The app cannot replicate
that offline; it must capture the technician's answers and let the server do it.

```go
type IssueInput struct {
    Verdict             int         // 0 Non-Compliant, 1 Compliant, 2 Incomplete
    NextService         *time.Time  // only when the design asks for one
    CompletePmWorkOrder bool
    CompletePmJobCard   bool
    Notes               string
}
```

**The app currently sends `Verdict` (as `patient_safe`) and `Notes`. It sends
none of the other three and has no UI to capture them.** That UI is the real
certification work remaining, and it cannot be designed until the endpoint's
shape is agreed.

### Rules the app must respect, from `certificate_write.go` and `certificate_nextservice.go`

1. **Verdict is chosen, never defaulted** — *"a machine that failed its test has
   to be certifiable as having failed"*. Check whether the wizard pre-selects
   Compliant; if it does, that is a bug.
2. **A meter-based PM task has no computed next-service date.**
   `NextServiceProposal` returns false for `PmTaskType = 2`, because it comes
   round on readings not months. The technician must be asked. The old Delphi
   app had no branch for this and offered whatever was left in the date picker.
   `AssetPmTask.isMeterBased` now exists in this app for exactly this;
   **nothing consumes it yet**.
3. **A date must not move while a work order is open on it.** Either that work
   order is completed with the certificate — with the technician told *which*
   one — or nothing is touched at all.
4. **The job card is asked for separately**, because the person issuing the
   certificate may not be the person writing it up.
5. **The test date comes from where the test started, not from Save.** *"Two
   boxes for one fact is one of them being wrong."*
6. `ErrIncompleteTests` / `ErrIncompleteValues` — every line needs a verdict and
   a reading. The app checks both locally and agrees, but has no path to
   display a server refusal.

### Also needed before any write works

- **Client id generation.** `TestMobileID` exists (migration 023, applied to
  local/demo/safeline) but **nothing in the app generates one and there is no
  `uuid` package in `pubspec.yaml`**. The server reconciles with
  `ON CONFLICT ("…MobileID") DO UPDATE`, which is what makes a retry idempotent.
- **Signatures.** They are `bytea` and **do not cross the sync stream** — 3,796
  exist server-side and the captured stream carried none. `SaveSignature`
  validates PNG magic bytes and caps at 256 KB, so the desktop stores them
  fine; what is missing is transport from a handset. A certificate is not valid
  without them.

## The lesson that cost the most time today

**Seven read paths were still pointed at dead sources. Six were found by the
user hitting them.**

Assets stats → picker dialog → PM tasks → test equipment → templates → asset
detail. Each fix revealed the next, because **a dead read is invisible until
someone opens that screen**: the app compiles, the query runs, and the answer is
an honest empty list from a table with no rows. Asset detail was worse — it
called the Horse REST API and would have thrown.

Two things would have prevented the whole sequence:

1. **Audit structurally, not reactively.** Enumerate every provider and trace
   what it *ultimately* reads. A grep for the data source is not enough —
   `templatesByType` reached it through the *repository*, and that indirection
   is why the first sweep missed it.
2. **Make the wrong source unrepresentable.** `showAssetPicker` now takes
   `PowerSyncAssetDataSource`, so the compiler rejects the dead one. That is
   worth more than any individual fix.

**The audit is now complete for assets and certification.** Every provider
resolves to PowerSync except three that are correctly still on the old path:
the two repository constructors serving the Horse push queue, and
`certAssetLocalDataSource`, which nothing reads.

**Work orders have not been repointed at all.** Do the audit first this time.

**Do not hand-edit `powersync_schema.dart`.** Regenerate it in the Go repo and
re-copy. `test/sync/powersync_schema_test.dart` pins seven invariants; if one
fails the server changed shape — **tell the Go session rather than adapting**.
That is an agreed contract.

**`syncDatabaseProvider` is lazy.** Sync starts only because the dashboard
watches `syncStatusProvider`.

### Type traps, all covered by `powersync_types.dart`

- `numeric` arrives as a **string** — `"125896.00"`, `"2.00"`. This one bit:
  `TestTemplateTestEquipQty` cast with `as int?` would have thrown.
- `boolean` arrives as `0`/`1`
- dates, times and timestamps arrive as ISO **text** — `date()` cannot be
  applied to them in SQL
- **Always give queries an explicit `ORDER BY`.** PowerSync returns stream
  order otherwise, which changes between syncs. `TestOutput` must be
  `TestOutPutID` ascending — that is the server's contract
  (`certificate.go:593`), and it is what makes the tablet match the office copy.

## Two rules worth keeping

**An indicator must be able to reach every state reality can reach, including
the good one.** Four instances hit today: the sync chip could not go green
(sticky `downloadError`), the Horse badge could not reach zero (its errors are
cleared only by a sync that can never run again), the rep app's per-row orphan
alerts cannot clear, and a row in no bucket is silent forever. Noise that
cannot stop and silence that cannot start are the same defect.

**Read the destination before writing to it.** Two near-misses: a copy that
would have overwritten the Go session's own handover, stopped only by an
unrelated syntax error, and 330 MB pulled into the repo instead of the
scratchpad.
