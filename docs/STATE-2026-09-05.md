## ✅ THE OPEN BUG — RESOLVED, and it was not this app

**"Cert reached server but no test data" was a stale server binary, not a
client fault.** Reported by the Go session 2026-09-06.

The deployed binary on demo was **nine hours older than its source**, and its
column allowlist **silently dropped `TestOutputCertMobileID`**. That allowlist
drops unknown columns by design, so an older server is not broken by a newer
client — but for a *required* field that is indistinguishable from silent
discard. The lines uploaded, landed attached to nothing, and were counted as
applied.

**46 readings landed orphaned on that host. This device holds exactly 46 local
outputs — 23 on each of two certificates. They are ours.**

The hypothesis recorded here at the end of the session — "the batch contained
no line ops" — **was wrong.** The batch was built correctly and sent correctly.
The reasoning that produced it was sound (a batch is all-or-nothing, so a
certificate without lines means no line ops were sent) and the conclusion was
still false, because the premise silently did not hold on that build. Worth
remembering: *all-or-nothing* was true of the code and not of the binary that
was running.

### What changed server-side, live on demo

Build `v0.0.0-20260906075214-ee1bf3bfab8c`, commit `ee1bf3b`.

1. **A line must name its certificate.** A `TestOutput` op must carry exactly
   one of `TestOutputCertMobileID` or `TestOutputCertID`. Neither is refused,
   both is refused, and the batch is refused **whole, before a transaction
   opens**. This is a behaviour change: a batch that used to be accepted now
   returns **400**.
2. **Every response carries `enforces`** — including 400/409/422 — naming what
   that build guarantees: `cert_ref_required`, `batch_atomic`,
   `conflict_fields`, `issue_action`, `sign_action`.
   **A missing `enforces` key means "no guarantees", not "not yet deployed".**
   An old server is otherwise indistinguishable from a compliant one at exactly
   the moment it matters — which is the failure that produced the 46 orphans.

### What this app already does right

`SyncUploadOp.certificateLine` sets `TestOutputCertMobileID` and **throws** if
the caller also passes `TestOutputCertID`. That matches the new rule exactly and
needs no change. The 46 orphans happened despite the client being correct.

### What to do next

1. **Re-test the upload against the fixed server.** The client is believed
   correct; this is now a verification rather than a debug.
2. **Check `enforces` on the response** and treat its absence as an
   unguaranteed server. This is the guard that would have caught the stale
   binary, and nothing in this app reads it yet.
3. **The 46 orphans are on the server** and are the user's to decide about —
   they join the 8,850 pre-existing orphaned lines as a records question.

## ⚠️ SIGNATURES — they can now go up, but not come down

Revised 2026-09-06. **The write half is solved**; the read half is not.

A signature is **an action, not a column**. The two `bytea` columns are
deliberately not writable, so a signature travels as its own op:

```json
{"table":"TestCertificate","mobile_id":"<cert uuid>","action":"sign",
 "data":{"which":"tech","png":"<base64 PNG>"}}
```

- `png` is **standard, padded base64** — never URL-safe. `CertificateSignature`
  holds it already-encoded, so a re-queued signature cannot be re-encoded
  differently on a second attempt.
- `client_name` is **required** for `which: "client"` and refused on `"tech"`.
- Sign ops run **after** issue ops, and signing is the only write allowed after
  a certificate is issued. `toBatch()` orders them last for that reason.
- New 422 codes: `already_signed`, `no_client_signature`.
- A signature captured after the readings were already sent is a **separate
  batch**, so `CertificateUpload` carries a `queueKey` distinct from
  `mobileId` — without it the outbox would silently replace the first batch and
  the readings would never go.

**What is still open:** `bytea` crosses neither the sync stream nor the read
path, so a device cannot display a signature it did not capture itself. The
office renders the PDF from server data, so the printed certificate is only as
good as what was uploaded — which is now possible, but unproven end to end.

**Also still unexplained:** no client signature and no `client_name` was
captured on either local certificate, though the wizard has a facility-contact
field. That is a wizard question, not a transport one, and it is worth settling
before trusting the sign path.

## The upload contract

Full detail in `docs/sync-client-handover.md` §§11–14. The essentials:

```
POST /{company}/sync/upload     Bearer device token (a cookie gets 403)
{"ops":[
  {"table":"TestCertificate","mobile_id":"<uuid>","data":{...}},
  {"table":"TestOutput","mobile_id":"<uuid>",
   "data":{"TestOutputCertMobileID":"<cert uuid>", ...}},
  {"table":"TestCertificate","mobile_id":"<uuid>","action":"issue",
   "data":{"verdict":1,"next_service":"...","complete_pm_work_order":true,
           "complete_pm_job_card":false}}
]}
```

- **A line names its certificate by `TestOutputCertMobileID`**, never
  `TestOutputCertID` — the device cannot know the server key. A `0` there is an
  orphan, and the register holds 8,850 of those.
- **`verdict` is required and never defaulted.** `0` is Non-Compliant.
- **Unknown fields on an issue op are REFUSED, not dropped** — the opposite of
  the row-op allowlist. Spell the five exactly.
- **422 ≠ 400.** 400 means the app is broken; 422 means understood and refused,
  and retrying never helps. `not_found` also means out of scope.
- **Trust the 409 `differs` flag; never re-derive it.** The app sends JSON, so
  an int arrives as a double — a text comparison would call `9304` and `9304.0`
  different.

## Dead columns — a whole class of silent bug

**`AssetNextServiceDate` and `AssetLastServiceDate` are NULL on all 5,121
assets.** Not sparse — dead register-wide. A check written against either fires
for nothing while looking like it works.

This produced the expired-analyser bug: every instrument stayed selectable
because none was ever expired. **Calibration due is the instrument's
`AssetPmTask` schedule date**, read as
`max(PmTaskScheduleDate)` per instrument — a scalar subquery, never a join
(a join lists an instrument once per task), and never matched by description
(the register already spells it three ways). That mirrors the desktop, which
has done it since 2026-09-02.

**Two more places still read the dead column and are quietly wrong:**

1. The Assets screen's **"Service Due"** tile — can only ever be 0.
2. The **"SVC DUE"** badge in the asset list, and both service dates on asset
   detail.

An asset's next service almost certainly also lives in `AssetPmTask`, but that
is an inference and inferring the source is exactly the mistake that caused the
calibration bug. **Ask, do not assume.**

## The lesson that cost the most time

**Seven read paths were still pointed at dead sources; six were found by the
user hitting them.** Assets stats → picker dialog → PM tasks → test equipment →
templates → asset detail.

A dead read is invisible until someone opens that screen: the app compiles, the
query runs, and the answer is an honest empty list. Two preventions, both now
applied at least once:

1. **Audit structurally.** Enumerate every provider and trace what it
   *ultimately* reads. A grep for the data source is not enough —
   `templatesByType` reached it through the *repository*.
2. **Make the wrong source unrepresentable.** `showAssetPicker` takes
   `PowerSyncAssetDataSource`, so the compiler rejects the dead one.

**Work orders have not been repointed at all. Do the audit first.**
