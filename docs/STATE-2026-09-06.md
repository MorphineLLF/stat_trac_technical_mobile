# State — 2026-09-06

Supersedes `STATE-2026-09-05.md`. Read this one first.

## The headline

**A certificate now uploads, issues and comes back with a number.** This
morning none of that worked: readings landed attached to nothing, the upload
endpoint was unreachable by a real handset login, and the issue action had
never been called once.

Proved end to end from a clean install, signed in as a real technician:

```
8483   12 readings   13 ops sent / 13 applied   issued
8485   12 readings   13 ops sent / 13 applied   issued, both signatures
```

Both on `demo`, both with `TestTech "Athi Maphaha"` / `TestTechID 31` written
by the server from the authenticated token — never from our payload.

## What to test next, and why it has not been tested

**Neither of these has been exercised at all. Both are the conditions the app
is built for, and both are untested.**

### 1. No wifi and no cell data

Everything proved today was proved with signal. The offline path is designed
but unobserved:

- A certificate finished with no signal should queue and stay queued.
- Signal returning should drain it without the technician doing anything.
- The dashboard should say *"No connection — N still queued"* in amber, not
  report success and not report a failure.
- A signature captured offline travels in the same batch; one captured later
  travels on its own.
- The PDF is the one thing that genuinely cannot work offline until it has
  been fetched once — a certificate not yet on the server has nothing to
  render, and the server answers 409 for it. The app should say *"needs a
  moment of signal first"* rather than failing blankly.

Worth testing by turning the emulator's data off mid-wizard, not just before
it.

### 2. Multiple uploads

Every test so far has been one certificate at a time. Untested:

- Several certificates queued before any sync, drained in one go.
- Order: the queue sends oldest first, so work reaches the office in the
  order it was done. Confirm that holds.
- One refusal in the middle. **A rejection refuses only its own batch**, and
  a parked row is taken out of the pending set so the ones behind it still
  go — that design has never been exercised with real rows behind it.
- The 1 MB body cap. It is checked before sending now, but no batch has ever
  come close, and a certificate with many readings and two signatures is the
  shape that finds it.

## What changed today, in the order it mattered

### The upload path could not be reached by a real technician

`refuseHandset` on the Go side allowed a device token to reach `/photos` and
nothing else. `/sync/upload` and `/sync/token` were not on the list, so every
genuine `UserMobileOnly` login was turned away at the door. It had only ever
worked because the login used for testing was a rights-1 administrator that
bypassed the check.

Fixed on the Go side. **Athi (user 31) is still the only login on `demo` that
can sync** — the technician-app grant has to be ticked per login, and
migration 026 applied per company database. That is the user's to do and
neither repository can do it.

### A certificate was being issued by writing a column

Our row op sent `TestTech`, `TestTechID` and `TestCertPatientSafe`. The server
reads a certificate as **issued** when its technician name is non-empty —
`Issued()` is `TrimSpace(Tech) != ""`. So every certificate this app has ever
uploaded was marked issued by the row op, with `IssueCertificate` never
running: no completeness check, no totals, no `TestNextService`, no PM
schedule moved, no work order touched. The document existed, asserted a
verdict, and none of the rules that make it evidence had been applied.

It surfaced only when we finally sent an issue op and it collided —
`already_issued`, refusing the whole batch, readings included.

None of the three are sent now. The Go side refuses them outright with a 400
naming the column.

**The first fix was aimed at the wrong column.** `TestCertPatientSafe` carries
the verdict and the void state — `PatientSafe 3` is void — which made it a
plausible culprit, and it was wrong. `TestTech` was the one. Recorded because
the reasoning was sound and the answer was still wrong: the difference was
going and looking rather than inferring.

### A refusal that lost work was reported as success

`already_issued` and `already_signed` were treated as benign — archive, mark
applied, delete the queue row. That is right for a signature-only batch. It
is catastrophic for a batch that was also carrying the certificate and twelve
readings: nothing landed, and the row holding the reason was destroyed.

Benign now requires the batch carried **no certificate and no readings**. The
reason code describes the certificate; the batch describes what would be
thrown away by believing it.

The existing test asserted the unsafe behaviour using a batch shape that
never occurs in practice. A test that cannot see the bug because it uses the
wrong shape is worth more attention than the bug.

### The rest

- **Issue op built**: verdict (three named constants, never arithmetic —
  `PatientSafe 3` is void and an off-by-one would void a certificate), next
  service date, and the completeness rules enforced on the device before
  anything queues.
- **Next Service Due** sits on the details step beside the PM task, defaulted
  from the PM interval, never before the test date, **only on designs that
  ask for it**. The server writes what we send verbatim, so the date shown is
  the date the register holds.
- **The two PM completion flags were removed** at the user's instruction —
  closing a PM work order is the office's business. Both send `false`. With
  an open work order on the task the schedule does not move; the certificate
  still carries the date.
- **PDF and email** work against the live Go routes with the device token.
  The PDF caches to disk, so one fetched is one viewable offline.
- **A facility signature can be added after issue**, gated so it is only
  offered where the design asks and nobody has signed.
- **413 and 401** no longer jam the upload queue.
- **Hospital shows on the certificate list**, with search.

## Traps recorded, so they are not re-learnt

**Do not join PowerSync tables.** A PowerSync table is a view over JSON with
no index on an arbitrary column. Joining `TestCertificate` to `Asset` scanned
the whole asset store per certificate; the query never returned and the list
showed a spinner for ever — no error, no empty state. Fetch separately and
attach in Dart, with a timeout, degrading to no hospital rather than no list.

**Every `FilledButton` in this app is full width.** `filledButtonTheme` sets
`minimumSize: Size.fromHeight(48)`, which is `Size(double.infinity, 48)`. One
placed in a `Row` demands infinite width, layout throws, and it throws again
every frame — which reaches a technician as an app that has hung, not as an
error. Widget tests for anything with buttons must pump the **real**
`appTheme`; under a default `ThemeData` they pass while the app freezes.

**A SnackBar shown from a bottom sheet renders behind it.** The signature
sheet refused to save and hid its own reason, so Save looked dead. Messages
inside a sheet belong inside the sheet.

**`applied` counts row ops only.** Issue ops and sign ops never touch it, so a
signature-only batch has `applied == 0` on success. Anything reasoning about
"did this land" must not use `applied` alone — it is `applied + issued +
signed`, or better, a structural check of what the batch carried.

## The shape of nearly every bug found today

Six of them, and they are the same shape: **a signal that could not reach the
state reality was in.** An applied count blind to orphans. A column allowlist
dropping a required field without a word. `/metrics` unable to see a route
that panicked on every call. A green "Sent 0 certificates". A list that
spun for ever with no error. A refusal reported as done.

None of them failed loudly. Each was worse than a crash, because something
was watching and being told everything was fine. Worth treating as the thing
to go looking for rather than a run of bad luck.
